# v1.0 — Integrated Game Production — Readiness Plan

Status: **PLANNING — NO RELEASE OR RUNTIME AUTHORITY**

This document freezes the readiness contract for the canonical `v1.0 — Integrated Game Production` milestone. It is milestone/readiness planning, not a new numbered architecture phase. It adds no production authority, does not change package version `0.5.0`, does not create or move a tag, and does not declare a v1.0 release.

The exact planning base is fully closed Phase-55 `main`:

```text
b3b04ce2c2c5380e933dc8cb4026da137dd8f3be
```

At this base, the canonical roadmap has no defined Phase 56. Phase 55 is DONE and the next named roadmap boundary is `v1.0 — Integrated Game Production`.

The absence of a numbered phase does **not** mean release readiness may assume that the representative integrated production goal is already achievable. v1.0 readiness must first map every milestone capability to current production-authoritative evidence and must stop whenever satisfying a target would require new runtime, schema, dispatch, backend, semantic-input, adoption, acceptance, signing, UI, or release authority.

---

## 1. Canonical v1.0 target

The roadmap representative Goal is:

> Create a slow heavily armored enemy that lives in abandoned factories and attacks with a large mechanical hammer.

The roadmap says Origin Forge should eventually coordinate:

```text
design specification
gameplay implementation
behavior
tests
2D/3D assets
textures
animation
sound
loot/configuration
integration
runtime verification
provenance
```

while allowing the human creator to inspect, reject, refine, or replace any part.

Readiness therefore means more than proving that isolated subsystems exist. The v1.0 acceptance audit must prove that the required semantic inputs can be created through reviewed authority, routed through the governed production chain where intended, independently validated, explicitly accepted where semantic authority is required, and composed without relying on hidden manual state that the representative Goal cannot produce.

## 4. Known milestone gaps that force a stop before release

### 4.1 Design specification — BLOCKED

Phase 32 defines the semantic capability:

```text
design.specify
```

but explicitly states that it has **no built-in executor**. It is known semantic work, not routable production work.

The v1.0 representative Goal begins from high-level design intent. Readiness may not pretend that a design specification exists merely because the production Planner can create Tasks or because Phase-17 Project Intelligence/Design Bible can store canonical semantic state.

A future implementation must separately define how design intent becomes bounded durable design-specification evidence and what authority, if any, may make that evidence canonical. A model proposal alone must not become project truth.

### 4.2 2D asset creation / textures / animation source — PARTIAL, RELEASE-BLOCKING

Phase 48 promotes exactly:

```text
media.2d.export
→ originforge.pixelorama.export
→ pixelorama.spritesheet-export@1
```

The production WorkOrder requires an **already-existing project-owned `PIXELORAMA_PROJECT` Artifact** representing exact `.pxo` source bytes.

The accepted Pixelorama production boundary explicitly does not provide:

- project creation;
- import;
- editing;
- save;
- arbitrary Extension API authority;
- model-generated editor scripts;
- automatic generation of `.pxo` source state.

Therefore Phase 48 can export reviewed existing Pixelorama project state, but it cannot by itself create the 2D source state required by the representative v1.0 Goal.

Phase 21 image generation is a separately governed proven substrate, but current Phase-34/production-dispatch history did not promote `originforge.image.generate` into the Manager production chain. The v1.0 audit must not silently equate an isolated generation API with integrated production authority.

### 4.3 3D semantic request creation — PARTIAL, RELEASE-BLOCKING

Phase 51 successfully promotes Blender GLB execution from one protected semantic request:

```text
MODEL3DREQ-*
```

but the frozen Phase-51 architecture states that a trusted programmatic producer may publish an already-valid semantic request and that Phase 51 adds **no model/Goal/Task metadata parser and no arbitrary creation CLI merely to manufacture 3D authority**.

The production WorkOrder selects exactly one pre-existing protected request from infrastructure-owned authority. This is correct for execution safety, but it leaves a v1.0 integration question upstream: how does the representative Goal create or approve the `MODEL3DREQ-*` that describes the desired enemy geometry/animation intent?

Readiness may not classify 3D production as fully integrated until that semantic-input authority is explicit and accepted.

### 4.4 Audio production dispatch — SUBSTRATE EXISTS, INTEGRATED PRODUCTION BLOCKED

Phase 22 provides governed audio substrate and real FFmpeg/Piper evidence.

Phase 32 includes inert production adapter descriptors for:

```text
originforge.audio.ffmpeg
originforge.audio.piper
```

but the accepted Phase-34 built-in review deliberately leaves both fail-closed:

- FFmpeg lacks the complete exact source evidence required for a production `AudioSourceRef`;
- Piper still requires a complete Phase-33 audio request contract plus execution-owned runtime identities.

No later accepted phase through 55 promotes audio into the Phase-33/34/35/36/37 Manager production path.

The v1.0 `sound` target is therefore not yet an integrated production vertical.

### 4.5 Runtime observation and playtesting — SUBSTRATES EXIST, INTEGRATED PRODUCTION BLOCKED

Phases 23 and 24 provide governed runtime-observation and cooperative-playtesting substrates.

Phase 32 contains:

```text
originforge.runtime.observe
originforge.playtest.cooperative
```

but Phase 34 deliberately defers both because exact typed production request/scenario readers were not available at that boundary.

No accepted phase through 55 promotes those adapters through production binding/claim/execution ownership.

The v1.0 `runtime verification` target therefore requires a separately accepted production-integration decision. Existing standalone observation/playtest evidence may remain advisory and must not be upgraded into Task PASS or semantic correctness without an explicit authority design.

### 4.6 Image generation / vision — SUBSTRATES EXIST, INTEGRATED PRODUCTION BLOCKED

Phase 21 proves bounded image-generation and advisory vision boundaries.

Phase 32 includes:

```text
originforge.image.generate
originforge.vision.inspect
```

but Phase 34 deliberately leaves both fail-closed because complete exact typed production request/model relations were unavailable.

No later phase through 55 promotes these adapters into the governed production dispatch chain.

Vision remains advisory and must never become synthetic HUMAN_OPERATOR acceptance merely to satisfy v1.0 readiness.

## 6. Human inspection / rejection / refinement boundary

The current cockpit remains intentionally read-only. It provides bounded inspection and no production mutation authority.

Pixelorama and Blender canonical outputs have explicit human-operated adoption/acceptance/signing module commands, and their semantic acceptance authority is intentionally not model-, vision-, Manager-, browser-, conversation-, or UI-derived.

v1.0 readiness must explicitly map how the human can:

```text
inspect
reject
refine
replace
```

across every production family claimed by the milestone.

A future UI may expose existing governed application boundaries, but browser presentation code must not acquire direct Task/Artifact/Verification/adoption/acceptance/signing authority. UI convenience is not a justification for weakening currentness, no-replay, or HUMAN_OPERATOR semantics.

The separately active GUI workstream remains a presentation/application-client workstream and is not implicitly part of this readiness plan.

## 8. Stop / split rule

Readiness work must stop and create one or more separately planned architecture phases whenever satisfying a milestone target requires any of:

- a new semantic input object or canonical evidence type;
- a new protected non-creating reader/resolver;
- a new Phase-33 dispatch contract;
- a new Phase-34 binder;
- a new preparation owner;
- a new Phase-36 execution owner;
- a schema migration;
- a new backend/runtime/model dependency;
- a new adoption or Task-acceptance relation;
- new HUMAN_OPERATOR semantics;
- a new signing relation;
- a new mutating UI/browser route;
- weakened no-replay/currentness/trust boundaries.

Such changes are implementation phases, not release maintenance.

Release-readiness commits may never smuggle runtime authority into version/docs/test changes.

## 9. Dependency-first implementation order if the audit remains blocked

The first new implementation phase must target the earliest dependency that prevents the representative Goal from creating governed downstream work. The current planning-base evidence suggests this order for separate architecture review:

```text
1. governed design-specification production substrate / authority
2. governed semantic media-source/request creation from accepted design evidence
3. remaining production promotion for image/audio/runtime/playtest families as actually required
4. cross-family integrated acceptance run over one representative Goal
5. only then v1.0 release readiness / version / immutable tag
```

This list is a prioritization hypothesis, **not authority to implement all items in one phase**. Each authority-expanding phase must be independently architected, exact-head gated, and merged before the next begins.

Do not create one generic model/tool/media dispatcher to accelerate this sequence. Existing exact adapter families, typed evidence, and fail-closed boundaries remain the model.

## 12. CI and merge discipline

Every readiness or later implementation slice continues to use the normal authoritative workflow:

```text
python -W error::ResourceWarning -m unittest discover -s tests -v
```

on both Python 3.12 and Python 3.13.

For every mutable repository slice:

- freeze one exact candidate head;
- require both interpreters green on that exact head;
- verify bounded intended diff and zero unrelated drift;
- verify current `main` freshness and zero-behind state;
- inspect comments, reviews, and unresolved review threads;
- transition from draft only after gates are green;
- merge with an expected-head SHA guard;
- verify `main` equals the returned merge commit before starting the next slice.

A green superseded head never authorizes a later mutation.
