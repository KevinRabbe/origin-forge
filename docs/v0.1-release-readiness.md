# v0.1 Release Readiness

Status: **PRE-RELEASE — stacked on Phase 30 closure candidate**

This document governs the transition from the completed roadmap implementation work into the first useful release. It does not introduce a new numbered architecture phase and does not widen production authority.

## Release base

The release-readiness branch is intentionally stacked on the exact Phase-30 closure candidate rather than merged directly to `main` while Phase 30 is still gated.

The canonical order is:

```text
Phase 30 exact-head CI
        ↓
Phase 30 canonical DONE + merge
        ↓
rebase/re-root v0.1 readiness on merged main
        ↓
release packaging/docs exact-head CI
        ↓
version/license/tag decision
        ↓
v0.1 release
```

A green stacked release-readiness branch is useful evidence, but it cannot substitute for Phase 30's own merge gate.

### Installed operator commands

`origin-forge`

- durable control-plane operations;
- explicit Goal / Flow / Task / Run / Verification management;
- bounded worker proposal surface;
- governed sandbox inspection/verification.

`origin-forge-attempt`

- one existing Phase-6/8 bounded coding attempt;
- requires explicit files or deterministic automatic context;
- requires existing contained config/database state, current schema/project binding, and quiescent SQLite state before entering the authoritative writer path;
- uses the configured sandbox and one selected model invocation for that attempt;
- returns `SUCCEEDED`, `FAILED`, or `BLOCKED` evidence through the existing orchestration contract;
- emits bounded JSON for ordinary operator/configuration failures;
- does **not** expose Phase-7 retry recursion, automatic merge, or release authority.

`origin-forge-cockpit`

- `snapshot`
- `serve`

The cockpit command delegates to the Phase-30 read-only interface. Packaging does not add a mutation command, host override, browser/process launcher, model/tool execution hook, Artifact adoption/signing action, Dream promotion action, merge action, or release action.

## Release invariants

Release work must not weaken architecture merely for convenience.

1. **No release-only authority shortcut.** Packaging and documentation do not bypass Task, Verification, Artifact, provenance, promotion, merge, or release gates.
2. **No hidden installer side effects.** Importing or invoking help for packaged commands must not initialize/migrate a project, load a model, acquire a resource lease, run an external tool, or mutate a repository.
3. **Attempt means one bounded attempt.** The installed attempt command exposes the existing single-attempt orchestrator and is not renamed or documented as an unlimited autonomous retry agent.
4. **Attempt preflight cannot initialize partial state.** Missing config/database, empty or stale database state, missing project binding, or active journal state must fail before the normal writer path rather than creating/migrating project state.
5. **Cockpit remains read-only.** The installed cockpit exposes exactly the bounded Phase-30 `snapshot` / `serve` surface.
6. **Development version until closure.** `0.1.0.dev0` remains until Phase 30 and release-readiness CI are green on their exact immutable heads.
7. **Licensing is explicit.** No license is inferred or auto-selected. Public distribution that requires a license decision remains blocked until the owner chooses one.
8. **Tagging is downstream evidence, not verification.** A Git tag does not substitute for the exact-head test/review gates.

## Explicit non-goals for v0.1 release hardening

Release hardening does not add:

- automatic merge or release authority;
- a new unbounded retry controller;
- UI mutation workflows;
- remote/multi-user cockpit hosting;
- arbitrary Artifact-byte/media preview serving;
- arbitrary shell/filesystem/process access;
- checkpoint/model activation;
- live self-training/self-modification;
- implicit provenance signing or trust verification;
- automatic Dream memory promotion.

Any such capability requires a separately governed future design rather than being smuggled into packaging or release scripts.

## Exit condition

v0.1 release readiness is complete when the actual merged Phase-30 mainline is packaged with discoverable, tested operator entrypoints; documentation matches the release tree; Python 3.12/3.13 tests pass on the exact release commit; licensing/version/tag decisions are explicit; and release mechanics add no new production authority.
