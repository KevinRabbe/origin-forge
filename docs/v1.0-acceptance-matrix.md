# Detailed evidence

## 1. High-level Goal → governed design specification

**Classification: `BLOCKED_ON_IMPLEMENTATION`.**

Accepted evidence:

- Phase 17 provides durable canonical Project Intelligence and structured Design Bible rules with infrastructure-owned identity/revision semantics.
- Phase 31 provides a bounded Goal-revision/hash-bound Planner and Task DAG materialization.
- Phase 32 defines the semantic capability `design.specify`.

Decisive blocker:

Phase 32 explicitly states:

```text
design.specify intentionally has no built-in executor in v1
```

Therefore current infrastructure can represent semantic project truth and can plan Tasks, but it does not yet own a governed production operation that transforms one high-level Goal/design Task into bounded durable design-specification output through reviewed authority.

A model-generated text response, Planner proposal, Task objective, conversation message, or UI field must not be promoted to canonical design truth by implication.

**Earliest dependency:** this is the first blocker in the representative Goal lifecycle and therefore owns next-phase priority.

# Earliest dependency and next architecture

The earliest blocker in the representative production lifecycle is `design.specify`.

The next architecture phase is therefore named:

```text
Phase 56 — Governed Design Specification Production Substrate
```

Phase 56 must be planned separately from this matrix. R1 grants it no implementation authority.

At minimum its architecture must answer, before code is changed:

1. What is the bounded durable design-specification object/evidence model?
2. What exact Goal/Task revision and Design Bible/Project Intelligence state does it bind?
3. Is model output proposal-only, and what independent audit/acceptance boundary makes any specification canonical?
4. Does design output become an Artifact, protected semantic object, Project Intelligence object, or a deliberately separate immutable family?
5. What authority may publish/supersede/retire a design specification?
6. How may Phase 31 PlanningInput consume the accepted design specification without caller/model ID substitution?
7. How are stale Goal revision, Design Rule drift, Project Intelligence drift, duplicate/competing specifications, restart, and ambiguous post-publication state handled?
8. What remains permanently outside Phase 56: Task execution, media creation, acceptance, signing, UI mutation, merge, deploy, release?

The preferred dependency direction is:

```text
high-level Goal
→ governed bounded design-spec proposal/evidence
→ explicit independent acceptance/canonicalization boundary
→ exact accepted design-spec identity/hash
→ Phase-31 planning consumes that exact evidence
→ downstream production Tasks
```

This is a conceptual target, not a frozen implementation contract. The Phase-56 architecture PR must establish the exact authority model before any implementation slice starts.
