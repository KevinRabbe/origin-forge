# Phase 0 Implementation Specification

Status: **Baseline for Phase 1 implementation**

This document converts the architecture into implementation contracts. Phase 1 should follow these contracts unless an explicit architecture decision changes them.

## 1. Initial runtime boundary

Origin Forge begins as one local Python application with internal modules.

Do **not** begin with microservices.

Initial process responsibilities:

```text
CLI
 ↓
Application service
 ↓
State layer / Scheduler / Policy / Provenance
 ↓
Model adapters + Tool adapters
 ↓
Local project workspaces
```

Separate processes are permitted for external runtimes such as model servers, language servers, Pixelorama, Blockbench, and other tools.

## 2. Initial technology baseline

```text
Language: Python 3.12+
State: SQLite
Version control: Git
Configuration: TOML or YAML at application boundary; JSON for structured interchange where useful
Local model transport: OpenAI-compatible local HTTP where available
Code search: ripgrep
Syntax parsing: Tree-sitter
Code intelligence: Language Server Protocol
```

Phase 1 itself should require only Python standard-library functionality plus the minimum SQLite/migration support required by the chosen implementation.

Dependencies must be justified individually.

## 3. Identifier format

Canonical IDs contain a type prefix and a globally unique opaque value.

Recommended display form:

```text
GOAL-<uuid>
FLOW-<uuid>
TASK-<uuid>
DEC-<uuid>
CHG-<uuid>
ART-<uuid>
VERIFY-<uuid>
RUN-<uuid>
```

Implementation may use UUIDv7 when practical for time-sortable identity. UUIDv4 is an acceptable temporary fallback if it avoids adding a dependency during the first implementation.

Rules:

- ID identity never depends on mutable names or file paths.
- IDs are generated by infrastructure, never by the LLM.
- IDs are never recycled.
- Human-friendly sequential numbers may be added later as display aliases only.

## 4. Time representation

Persist timestamps in UTC.

Application/database boundary representation:

```text
RFC 3339 / ISO-8601 UTC
```

No business logic should depend on local workstation timezone.

## 5. Database ownership

SQLite is canonical durable state for runtime metadata.

Models do not receive arbitrary SQL execution.

All writes go through typed application services/repositories that enforce:

- allowed state transitions
- revision checks
- foreign-key relationships
- append/history rules
- authority checks where relevant

Use foreign-key enforcement from the first migration.

## 6. Database files

Initial per-project state location:

```text
<project-root>/.origin-forge/
├── project.db
├── config.toml
├── design/
├── manifests/
├── references/
└── runtime/
```

Global user-level state may later live under an Origin Forge application-data directory.

The company root private key must **not** live inside ordinary project state.

## 7. Core state tables

Phase 1 minimum tables:

```text
projects
goals
flows
tasks
decisions
changes
artifacts
verifications
runs
state_events
schema_migrations
```

Company/Product/Entity/Skill/Tool/Model tables may be added during their corresponding phases unless required earlier by provenance experiments.

## 8. State event journal

Meaningful durable state transitions should append an event record.

Minimum event fields:

```text
id
aggregate_type
aggregate_id
event_type
old_state
new_state
revision
actor_type
actor_id
metadata_json
created_at
```

Examples:

```text
FLOW_CREATED
FLOW_BLOCKED
TASK_STARTED
TASK_FAILED
TASK_SUCCEEDED
VERIFICATION_RECORDED
```

The journal supplements current-state tables; it does not replace them.

## 9. Flow state machine

Allowed Flow states:

```text
QUEUED
RUNNING
WAITING
BLOCKED
FAILED
QUARANTINED
SUCCEEDED
CANCELLED
```

Initial permitted transitions:

```text
QUEUED → RUNNING
QUEUED → CANCELLED

RUNNING → WAITING
RUNNING → BLOCKED
RUNNING → FAILED
RUNNING → QUARANTINED
RUNNING → SUCCEEDED
RUNNING → CANCELLED

WAITING → RUNNING
WAITING → BLOCKED
WAITING → CANCELLED

BLOCKED → RUNNING
BLOCKED → FAILED
BLOCKED → QUARANTINED
BLOCKED → CANCELLED

FAILED → RUNNING        # explicit retry/reopen
FAILED → QUARANTINED
FAILED → CANCELLED

QUARANTINED → RUNNING   # explicit privileged recovery
QUARANTINED → CANCELLED

SUCCEEDED → terminal
CANCELLED → terminal
```

`SUCCEEDED` is immutable except through a future explicit superseding Flow, not reopening the same successful record.

## 10. Task state machine

Allowed Task states:

```text
QUEUED
READY
RUNNING
WAITING
BLOCKED
FAILED
QUARANTINED
SUCCEEDED
CANCELLED
```

`READY` means dependencies are satisfied and the scheduler may assign execution.

A Task may reach `SUCCEEDED` only after its required acceptance criteria have associated passing Verification records.

An Executor result alone cannot set `SUCCEEDED`.

## 11. Optimistic concurrency

Durable mutable records such as Flow and Task carry an integer `revision`.

Mutation contract:

```text
read revision N
attempt update WHERE revision = N
set revision = N + 1
```

If zero rows update, the caller has stale state and must re-read before retrying.

Never silently apply last-write-wins to Flow control state.

## 12. Goal contract

A Goal contains:

```text
objective
success_criteria[]
constraints[]
budgets
priority
status
```

Success criteria should be machine-checkable wherever possible.

Example:

```text
build passes
all required tests pass
artifact exists
runtime interaction succeeds
```

Subjective criteria may reference a critic/audit procedure rather than pretending to be deterministic.

## 13. Task contract

The Manager creates Tasks with this conceptual structure:

```text
TaskContract
├── objective
├── acceptance_criteria
├── constraints
├── required_capabilities
├── relevant_entity_ids
├── relevant_decision_ids
├── allowed_tool_scopes
├── budget
└── expected_outputs
```

The Executor receives the TaskContract as immutable task authority.

If a Task cannot be completed within its contract, the Executor returns a blocked/failure finding rather than expanding scope itself.

## 14. Executor result contract

An Executor returns a structured result such as:

```text
ExecutorResult
├── status: COMPLETED | BLOCKED | FAILED
├── summary
├── proposed_changes[]
├── produced_artifacts[]
├── observations[]
├── unresolved_questions[]
├── verification_requests[]
└── metrics
```

`COMPLETED` means the Executor believes its bounded work is ready for audit. It does **not** mean the Task is verified.

## 15. Auditor result contract

An Auditor returns:

```text
AuditResult
├── status: PASS | FAIL | INCONCLUSIVE | BLOCKED
├── findings[]
├── verification_records[]
├── regression_findings[]
├── evidence_refs[]
└── metrics
```

The Auditor should use read-only access wherever possible.

A failing Audit creates actionable findings for a new Executor attempt rather than silently changing the artifact under review.

## 16. Tool contract

Every tool eventually implements metadata equivalent to:

```text
ToolSpec
├── id
├── name
├── version
├── description
├── input_schema
├── output_schema
├── permissions
├── side_effects
├── deterministic
├── reversible
├── resource_requirements
├── timeout_policy
└── verifier
```

Tool invocation always passes through:

```text
schema validation
→ authority/policy check
→ before_tool_call hooks
→ invocation
→ result capture
→ after_tool_call hooks
→ observability record
```

## 17. Model adapter contract

Model adapters expose a common conceptual interface independent of provider/model family.

```text
ModelRequest
├── role/capability target
├── messages/context
├── available_tool_interface
├── structured_output_schema
├── token budget
├── timeout
└── sampling/reasoning options
```

```text
ModelResponse
├── text/structured result
├── tool requests
├── usage
├── timing
├── finish reason
└── runtime metadata
```

The application never stores model-provider-specific response objects as canonical project state.

## 18. Model profile contract

A ModelProfile eventually records:

```text
capabilities
runtime adapter
model identity/hash
quantization
context limit
recommended working context
VRAM/RAM requirements
tokens/sec
benchmark results
preferred task classes
```

Routing decisions should depend on profiles and benchmark evidence rather than model-brand conditions spread through the codebase.

## 19. Context package contract

A fresh Executor receives a generated ContextPackage.

```text
ContextPackage
├── goal_summary
├── task_contract
├── relevant_entities
├── relevant_decisions
├── relevant_verification_state
├── selected_skills
├── selected_tool_descriptions
├── source_context
└── budget
```

The package must be reproducible enough to record what information was supplied to a Run without requiring raw hidden reasoning to be retained.

## 20. Skill contract

Initial Skill package convention:

```text
skills/<skill-name>/
├── SKILL.md
├── skill.yaml
├── references/
├── schemas/
├── scripts/
├── examples/
├── tests/
└── evals/
```

`skill.yaml` conceptual fields:

```text
name
version
description
required_tools
required_capabilities
permissions
dependencies
resource_requirements
verification
```

Skills are not required in Phase 1, but the architecture must leave a clean insertion point.

## 21. Hook contract

Hooks are deterministic infrastructure callbacks.

Initial lifecycle names:

```text
before_task
after_task
before_model_call
after_model_call
before_tool_call
after_tool_call
before_file_write
after_file_write
before_verification
after_verification
before_merge
after_merge
before_context_compaction
after_context_compaction
```

A hook may:

- observe
- enrich metadata
- block an action with a typed reason
- trigger deterministic validation

Hooks do not receive permission to bypass the authority system.

## 22. Authority decision contract

Every side-effecting operation produces an authority decision:

```text
ALLOW
DENY
REQUIRE_APPROVAL
```

The decision includes:

```text
rule_id
reason
scope
actor
operation
resource
```

The model may receive the reason but cannot modify the decision.

## 23. Initial filesystem policy

Phase 2 default:

```text
Read:
  current project
  approved references

Write:
  current Task worktree only

Deny:
  paths outside approved roots
  Origin Forge security/control-plane files unless explicitly authorized
```

The policy is enforced by tool implementations, not prompt instructions.

## 24. Git workspace contract

For side-effecting coding Tasks after worktree support exists:

```text
base commit
→ create Task worktree/branch
→ execute modifications
→ verify
→ produce diff
→ review
→ merge separately
```

Persist:

```text
task_id
base_commit
branch/worktree
head_commit (when committed)
merge status
```

## 25. Retry policy

Retries are typed.

```text
TRANSIENT_RETRY
STRATEGY_RETRY
MODEL_ESCALATION
HUMAN_ESCALATION
```

Identical failures do not consume unlimited retries.

Initial conservative default:

- maximum 2 equivalent strategy retries before escalation
- maximum 3 equivalent verification failures before Task quarantine unless policy overrides

Exact values should become configuration and later benchmark-driven.

## 26. No-progress detection

Track a rolling signature of:

```text
tool name
normalized arguments
result/error class
verification delta
```

No-progress conditions include:

- repeated same tool/args/result
- repeated identical test failure with no changed relevant artifact
- repeated patch/revert oscillation
- zero verification improvement across configured attempts

The loop detector returns a typed finding to the Manager.

## 27. Observability contract

Every Run should record at minimum:

```text
run id
task id
role
model profile/tool workflow
start/end time
status
model calls
tool calls
input/output tokens where available
failure reason
resource metrics where available
```

Detailed trajectories may be stored separately from canonical project truth.

## 28. Provenance boundary

Phase 1 records lineage fields even before cryptographic signing exists.

The acceptance path should eventually be:

```text
produced artifact
→ hash
→ lineage record
→ verification
→ signed manifest
→ accepted artifact
```

Signing and watermarking are later phases, but early schema choices must not make provenance retrofitting difficult.

## 29. Recovery contract

On startup the runtime must be able to discover incomplete work.

For every `RUNNING` Flow/Task/Run, recovery determines:

```text
is authoritative process still alive?
what worktree/resource belongs to it?
was a result persisted?
was verification completed?
was anything merged?
```

When uncertain, prefer `BLOCKED`/reconciliation over assuming success.

Recovery operations should be idempotent.

## 30. CLI scope for early phases

Initial CLI should stay small.

Conceptual commands:

```text
origin-forge init
origin-forge status
origin-forge goal create
origin-forge flow show
origin-forge task show
origin-forge run recover
```

Agent-facing commands arrive only when their backing state model is ready.

## 31. Project configuration

Initial `.origin-forge/config.toml` should hold project-local configuration, not secrets.

Potential fields:

```text
project identity
repository settings
allowed build/test commands
model profile names
resource budgets
policy profile
```

Secrets belong in a separate secure mechanism and are referenced indirectly.

## 32. Migration discipline

Every database change uses a numbered migration.

Rules:

- no editing old applied migrations
- migration application is transactional where SQLite permits
- schema version is recorded
- tests cover upgrade from the previous supported schema

## 33. Phase 1 test strategy

Before any LLM integration, tests should prove:

1. database initializes consistently
2. IDs are unique and correctly typed
3. invalid state transitions fail
4. valid state transitions append events
5. stale revisions are rejected
6. restart/reopen preserves state
7. successful states are not silently reopened
8. foreign-key integrity is enforced
9. recovery identifies interrupted RUNNING records
10. repeated recovery is idempotent

## 34. Definition of Phase 0 complete

Phase 0 is complete when:

- README describes the project accurately
- architecture is documented
- core object semantics are documented
- security/authority model is documented
- roadmap is documented
- implementation contracts are documented
- unresolved choices that would block Phase 1 are explicitly listed

## 35. Known deferred decisions

These do not block Phase 1:

- final public/commercial license
- permanent company legal/brand identity
- exact cryptographic algorithms/key-storage implementation
- final watermark algorithms
- final GUI framework
- exact image/audio/vision models
- whether a custom trained model is ever needed

## 36. Phase 1 start point

The first code should implement:

```text
package skeleton
configuration loader
SQLite connection/migrations
ID utility
Goal/Flow/Task repositories
state-transition service
state event journal
restart/recovery inspection
unit tests
minimal CLI
```

No LLM call is required to prove Phase 1.
