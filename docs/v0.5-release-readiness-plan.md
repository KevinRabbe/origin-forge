# v0.5 — Integrated Development Infrastructure — Release Readiness Plan

Status: **PLANNING — NO RELEASE OR RUNTIME AUTHORITY**

This document freezes the release-readiness contract for the canonical `v0.5 — Integrated Development Infrastructure` milestone. It is release-maintenance planning, not a new numbered architecture phase. It adds no production authority, does not change the package version, does not create or move a tag, and does not declare a release.

The planning base is exact merged Phase-47 `main`:

```text
a65a3e78ae3c6fb762cbe5f46a510adf22804c49
```

## Why this milestone is next

The canonical roadmap contains no Phase 48. Its next named boundary after Phase 47 is v0.5, whose target capabilities are already represented by accepted implementation on current `main`:

- durable long-running work;
- local coding models;
- governed Skills + Skill evaluation;
- structural/LSP code intelligence;
- progressive tool discovery;
- model/resource scheduling;
- offline memory consolidation and audited improvement proposals;
- specialist review;
- project graph + Design Bible;
- cryptographic provenance;
- basic 2D production.

Post-v0.1 Phases 31–47 additionally provide governed production planning, routing, WorkOrders, binding, claims, execution, bounded Manager operation, explicit Goal bootstrap, and deterministic simulation production dispatch. These later capabilities may be included in the v0.5 release payload, but they must not silently widen any authority boundary merely because they are packaged in the milestone release.

The remaining work is therefore release traceability, packaging/version readiness, operator documentation synchronization, and immutable release proof—not another speculative runtime feature phase.

## Release-readiness invariants

### 1. No numbered architecture phase is invented for release maintenance

v0.5 readiness is a milestone gate over already-accepted implementation. Runtime feature work discovered during readiness must be split into a separately planned architecture phase instead of being smuggled into packaging or documentation commits.

### 2. No release-only authority shortcut

Release work may not add or broaden:

- automatic Task success/failure authority;
- automatic Artifact adoption or provenance signing;
- automatic Dream/Workshop/training promotion;
- automatic merge, push, release, deployment, or tag authority inside Origin Forge;
- background Manager/Goal-bootstrap scheduling, queue draining, polling, watching, or daemon entrypoints;
- arbitrary shell/filesystem/process/model/tool authority;
- cockpit mutation or remote/multi-user hosting;
- dynamic production-owner/plugin dispatch;
- implicit simulation replay or Task terminalization from simulation findings.

### 3. Existing installed command count remains three

v0.5 does not require a fourth package entrypoint. Current post-v0.1 Manager and Goal-bootstrap operations remain subcommands of `origin-forge`; the cockpit remains read-only; `origin-forge-attempt` remains one bounded coding attempt.

### 4. Historical release identities remain immutable

- tag `v0.1.0` and its release commit are archival evidence and must not move;
- `docs/v0.1-*` documents remain historical v0.1 records;
- v0.5 receives its own release-readiness, acceptance, and operator snapshots rather than mutating v0.1 history.

### 5. Version transition is downstream of readiness evidence

Planning and the first readiness-audit slice retain `0.2.0.dev0`. A final release-candidate slice may transition package/test/docs identity to `0.5.0` only after the v0.5 acceptance matrix and packaging/operator boundaries are frozen and reviewed.

The roadmap milestone name is the source for the intended release line; no intermediate `0.2.0` release is implied by the current development version.

### 6. Tagging is final external evidence

An annotated `v0.5.0` tag may be created only after:

1. the final `0.5.0` candidate passes the normal Python 3.12/3.13 matrix on one immutable head;
2. review/thread state is clean;
3. that exact head is SHA-guarded merged;
4. `main` is verified at the resulting release commit.

The tag must point to that tested/reviewed release commit and must never be used as a substitute for CI or review.

- make no runtime/source/schema/config/authority change;
- run the full normal Python 3.12/3.13 matrix on the exact immutable candidate;

After the R2 merge only:

- create annotated tag `v0.5.0` on that exact commit;

- if a GitHub Release object is created, it must refer to that immutable tag/commit and add no repository mutation authority;
- record the completed immutable release evidence without moving the tag or rewriting historical v0.1 records.

If recording R3 evidence requires a repository documentation commit, that commit is explicitly post-release documentation and must not move the `v0.5.0` tag.

The release gate must continue proving at minimum:

- package metadata and Apache-2.0 identity are exact;
- Python floor/build-system floor remain explicit;
- installed scripts are exactly the existing three mappings;
- `origin-forge-attempt` remains one bounded context-selected attempt;
- attempt help/uninitialized/config-only/empty-database/cross-project/active-journal paths remain fail-closed and non-initializing;
- cockpit remains exactly `snapshot|serve`, loopback/read-only by existing subsystem tests, and non-initializing on help/uninitialized paths;
- current `origin-forge` Manager and Goal-bootstrap operations remain subcommands, not added package scripts or background services;
- no release-specific production mutation surface is added.

## CI and merge discipline

Every R0/R1/R2 repository mutation must use the existing normal workflow as the authoritative gate:

```text
python -W error::ResourceWarning -m unittest discover -s tests -v
```

on both Python 3.12 and Python 3.13.

For each slice:

- freeze one exact candidate head;
- require both interpreters green on that head;
- verify the intended bounded diff and zero unrelated drift;
- verify review submissions and unresolved review threads;
- verify `main` has not moved unexpectedly;
- transition from draft only after those checks;
- merge with an expected-head SHA guard.

No green result from a superseded head authorizes a later mutation.

## Stop / split conditions

Release readiness must stop and create a separately planned architecture phase if audit discovers that a canonical v0.5 target is not actually implemented or requires production-runtime behavior to satisfy it.

Release readiness must stop rather than silently broaden scope if satisfying packaging requires:

- a new installed command;
- a new daemon/service/background scheduler;
- a new model/runtime/provider dependency;
- a new schema migration;
- a new production authority path;
- a changed trust/provenance root;
- weakened fail-closed or no-replay semantics.

Documentation/version/test-only corrections consistent with already-accepted runtime behavior remain release-readiness scope.

This planning document is the only R0 repository delta. The exact planning head must pass the normal Python 3.12/3.13 matrix, review/thread state must be clean, and that exact head must be SHA-guarded merged before R1 begins.
